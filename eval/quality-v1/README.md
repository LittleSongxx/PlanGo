# 两指标评测设计材料 v1

**这是设计草案，不是已完成的评测成绩或已封存的盲测集。** 本轮只研究协议、起草公开开发案例并静态检查文件；没有执行被测模型、浏览器或任务批次。

- [完整协议](../../docs/质量评测协议.md)：TSR二元验收、事实切分/判分、分母、来源时效、金标复核、数据划分和统计口径。
- [任务草案](tasks.dev.json)：12条、6个家族。`agent_input`仅存用户输入；`environment`是评测器配置，不能直接作为模型提示词。
- [金标草案](gold.dev.json)：每条任务的must-pass、禁止结论、事实依据与可接受变体。全部由AI起草、待人审，不传给被测模型。
- [来源登记](sources.dev.json)：3份既有原始材料的文件/子树hash与2类显式受控材料。路径位于私有output，未复制数据库、profile或Cookie。只有注册的原始子树可作为候选来源，旁边的系统生成结果不可当gold。
- [静态检查记录](design-check.json)：12条任务/金标草案与3份原始子树hash核对通过；人审/留出/模型运行数量均为0，不产生质量分数。
- [划分计划](split-plan.json)：30条留出尚未采集、3条实时哨兵尚未执行；没有把旧门店改名成未见集。
- [任务评分空表](task-annotations.csv)、[事实评分空表](claim-annotations.csv)：没有填造分数。

这12条只覆盖“规范是否清楚、资料是否足够、评分器怎么检查”的公开开发用途，不能当独立样本估计泛化。包括真实记录派生与显式合成控制；合成初态/条款是评测资料，不是可用于正常运行的商家事实。评测器需要通过正常初始化建立别名对应的真实run/request ID，不能直接塞入成功状态绕过过程。

目前的关键阻塞是：原始来源人工审核、完整回放环境/业务时钟适配、独立金标与未见留出。尤其原始DOM文本的120/32元只保留相邻数字，不能推断原价标签；公交raw响应尚缺完整请求时间元数据。当前程序的解析结果不负责填补这些缺口。

可运行的命令只检查**设计文件结构和来源hash**，不会运行Agent或生成质量分数：

```bash
python3 scripts/check_quality_design.py
```

`design_valid=true`不等于`evaluation_ready=true`。在缺少私有原始文件的克隆中，检查会报告来源不可用并保持未就绪；如本地来源存在但hash改变，则报错。正式执行需要另行实现并验证runner，不能把现有四案例pilot直接指向新JSON后当作完整评测。
