# PlanGo：面向秋招简历与作品集的推进建议

2026-09-09；核实代码基线 `a05f037`，当前HEAD `46543d6`。本文件是建议，未启动功能实施、真实测评、窗口、部署或投递，不改变现有架构决策与“完整质量测评暂停”的约束。用户已确认主投AI应用／Agent开发；毕业届别、学历和目标JD尚未提供，因此不对具体职位录用资格作判断。

## 1. 结论与定位

建议将下一阶段中心从扩大业务覆盖转为：让招聘者迅速看懂、让关键主张可核验、让本人能独立解释和修改。当前已经具备写进工程类简历的项目基础，继续等真实预约/支付全闭环没有必要。推荐项目定位：

> PlanGo｜可恢复、可核验的本地生活 Agent 桌面工作台

核心叙事是“把模型规划、真实浏览器、工具授权和持久状态组成可交付产品”。优先展示可靠执行与故障恢复，其次是需求/证据一致性，第三是桌面产品交付。Agent运行时工程与GPU训练/推理Infra是不同方向。

## 3. 下一步的优先级

以下时间为工作量估计，受个人基础、可用时间和试用者配合影响；不是交付承诺。优先边准备边投递，不等项目“全部完成”。

| 优先级 | 推进事项 | 最小交付/验收 | 求职用途 |
| --- | --- | --- | --- |
| P0 | 明确主投方向与个人贡献 | 选一版主简历；列清上游/AI协作/本人决策与改造；3个技术问题能脱离AI讲清 | 防止项目很大但回答不了追问 |
| P0 | 做招聘者入口 | 一页作品介绍、3分钟录屏、30秒GIF、1张实际架构图、3个案例入口；给不了解项目的人看后能复述用途与难点 | 简历链接点开后立刻有内容可看 |
| P1 | 补任务级评估口径 | 先定义20个左右分层任务，再按明确预算少量重复；保留失败/外部阻断和原始记录 | 从“测试很多”变成“任务效果有定义” |
| P1 | 做一项有对照的优化 | 选择一个已知重复开销，固定输入/版本/模型/预算，对比请求数、tokens与用户等待，且正确性不退化 | 形成一条有测量结果的简历bullet |
| P1 | 让独立使用者试用 | 3–5位未参与开发者，各完成安装或2–3个明确任务；记录卡点、修复前后现象 | 证明交付能被别人使用，顺手改有证据的UI问题 |
| P2 | 有界补网页表单准备 | 仅在找到稳定真实入口时核对表单/版本/恢复；具体写入仍另行授权，找不到不继续消耗时间 | 补动作边界案例；不是开始投递的前提 |

### 作品集应怎样展示

首屏用产品用途、实际截图和视频入口；技术栈放在其后。建议内容顺序：一句话定位 → 30秒预览 → 3分钟完整演示 → 3个工程案例 → 指标/边界 → 试用与源码入口。面向招聘者的公开页面不应要求先下载108MiB包、安装Docker并配置模型密钥才能理解项目。先用静态介绍、录屏与来源清楚的历史回放即可；回放明确标记，不能冒充实时Agent。完整桌面包供愿意深入体验的人使用。

复用[已有Demo脚本](Demo脚本_3分钟.md)，将主线调整为：明确重庆需求 → 真实高德规划与来源 → 同run改人数/预算 → 保存草案 → 重开后恢复。真正有说服力的是修改和恢复过程，不必现场随机取号或登录商家来凑戏剧性。商家读取另用短片说明“哪些拿到了、哪些仍未知”。审批/丢回执可另做清楚标注的受控故障演示；视频若剪掉等待，应注明剪辑，不暗示3分钟就是实时执行耗时。

三个技术案例优先选：

1. 外部操作后丢回执：为什么不能简单重试，数据库事务能保证什么，UNKNOWN如何处理。
2. 同任务修改预算/人数/日期：如何区分未提及、清除和未知，为什么只刷新相关依赖，旧审批如何失效。
3. 消息历史倍增或旧观测盖住新卡片：具体反例、共享根因、最小修复、回归以及仍未证明的结论。

### 任务级指标与一项优化

建议先用小样本，而不是恢复完整质量大测评。本轮仅设计，不启动任何模型或高德实验。

- 分层覆盖清楚规划、多轮修改、来源不足、人工接管、故障恢复；案例在运行前定义所需结果与证据。20是建议样本数，不是已测数量。
- 规划成功只按可核对草案范围计数；正确暂停验证码是安全边界通过，不等于原业务任务成功。产品达标、外部阻断、安全检查分别统计，外部阻断不偷偷删出分母。
- 记录每任务/每轮的真实tokens、调用数、用户端到端耗时；人工等待与模型服务耗时另列。小样本先给中位数、范围与逐次值，不包装p99或生产SLA。
- 用冻结页面做可重复抽取/故障测试时标明受控回放；少量真实页面检查单列。固定输入、模型、预算与冷热缓存条件，保留旧失败，不清累计，不抬预算。
- 有日志依据的候选优化：已锁定单站且只改人数时，是否还需要刷新全部候选并向多个视角传全部证据。历史曾尝试20个身份、14个成功，两份Advocate输入各约9.2k tokens；这是旧记录，不是已经测得的优化收益。只有验证锁定站身份、日期天气、路线与未知供给仍正确，才可收敛候选范围并写改善指标。[依据](真实用户回归.md)

### 个人贡献与面试准备

先做一张轻量表：组件/场景、继承基线、本人提出的决策、AI协作内容、本人能独立修改的代码、证据。固定上游来源在[SNAPSHOT](../vendor/plango_harness/SNAPSHOT.json)；不读取兄弟项目来推断归属。若上游同样是用户作品，应单独确认，不把“源路径在自己的电脑上”当证明。

AI辅助开发本身不需要遮掩。关键是能解释取舍、判断生成代码的错误、维护结果并对边界负责。仓库提交与测试通过不能单独证明本人独立编写全部代码；“主导/负责人/完全自研”需职责证据。至少练习脱离AI完成一次小修改并写出能失败的回归，例如稀疏补丁新增字段、旧审批拒绝或回执重传；这是建议，尚未验证个人能力。

简历保留一行定位和约3条主线：任务编排/规范一致性、授权与可靠恢复、验证与交付。使用外部面试官能懂的词，具体私有函数与几十个枚举放作品集证据索引。可先使用已有定性能力，不等量化补完；没有实测数据就不要写百分比。

### 补清“模型到底做了什么”

作品集需明确画出模型边界：模型负责自然语言需求理解、规划候选与有限工具选择；确定性代码负责字段校验、价格/来源核对、权限、预算和恢复。首站规则适配只证明特定版式读取，不冒充通用网页理解；LLM规划和受控执行的价值用另外的真实主线展示。不要把多角色数量或ReAct术语当作智能效果证据。

AI应用岗位的候选实验应围绕实际用户任务：同一需求的槽位提取是否正确、工具参数是否可靠、修改后能否保持约束、遇到不确定信息是否正确停止。规划、工具选择与事实核验分别归因，比只测最终文本看起来是否漂亮更能解释模型工程能力。

## 4. 暂缓什么

- 不继续为“功能更完整”扩一批商家、支付、真实预约或消息渠道；App-only站点的限制已经有证据。
- 不为关键词数量增加Agent、MCP、OpenAPI生成、OTel部署或另一个框架。目标JD与真实接入需求同时成立时再加。
- 不为补RAG关键词另建通用聊天知识库。如果目标岗位确实看重检索，优先在已有来源/偏好/记忆场景补检索效果与遗忘验证，不能把pgvector依赖或opt-in embedding写成已验证RAG成果。
- 不为投Java/Go岗位整仓重写。先核实语言要求与个人基础，现有工程经验可迁移，缺失的语言能力单独补。
- 不优先做全平台安装器；先确认目标受众使用环境。现有Linux/WSLg包之外，另一人/另一设备的成功试用比只生成更多安装文件有价值。
- UI继续改有证据的阻塞、可读性和状态问题，暂缓装饰性重设计。

## 5. 约两周的建议安排

第1–2天：落实已确认的AI应用／Agent定位、贡献表、作品首屏与3分钟脚本；已有项目即可开始写简历和投递。

第3–5天：录屏/截图/架构图和2个技术案例，整理小任务集与指标口径。

第6–8天：一项有对照的窄优化、独立使用者试用，修最影响完成任务的UI/安装问题。

第9–10天：补第三个案例、定稿Agent应用主简历；按实际JD再准备侧重后端或客户端的版本，准备15分钟讲解与追问；同步投递，不等真实交易闭环。

若时间只够3天：贡献与定位 → 视频/作品入口 → 三条简历与一次项目模拟面试。算法/计算机基础准备应并行，项目不能替代笔试与基础面试。

主投方向已确认；这份建议仍可结合具体JD、毕业届别/学历、可投入时间及个人职责继续细化；没有写入已确认架构决策、没有自动恢复测评、没有发布网站/推送仓库或联系试用者。
