# PlanGo 作品集主线与复杂度审查

2026-09-09，独立子Agent只读核查源码、实际调用者和已有验收材料；这是工程审查，不是招聘市场调查。改进后的质量与部署状态另见[当前交接](CODEX_HANDOFF.md)。

PlanGo 的主线能够清楚描述：**基于门店资料比较优惠，在同一任务中修改人数、日期和预算，保留来源与待核验项，保存草案并在中断后继续。** 当前适合作为有可恢复工程链路的 AI 应用作品；已有局部开发验收，独立使用及新表达可靠性仍需补证。

## 主线与证据

| 用户步骤 | 实际代码与约束 | 证据边界 |
| --- | --- | --- |
| 选店及优惠 | `OfferComparisonCard` → `DesktopRuntime.select_offer`，绑定 command/artifact/hash、canonical POI 与人工同店确认 | 来源引用不能替代完整优惠规则 |
| 改人数、日期、预算 | `RequirementsCard` 仅发变化字段 → `/requirements` → 共用 replan、TripSpec 和版本校验 | 明确结构化字段正确不等于任意自然表达正确 |
| 看适用性与缺失项 | `compare_offers`、`source_analysis` → 成果卡与真实回复 | 核算、原文和范围均要正确，不能仅凭卡片存在判通过 |
| 保存草案 | `draft_decision` 校验 interrupt、plan ID/version | `draft_ready` 是保存结果，不是商家履约 |
| 中断继续 | store 先持久化请求身份，`deliver/checkDelivery` 取回原请求；SSE 按序补齐 | UNKNOWN 不可重放；恢复不续授权或重置累计预算 |

[产品接续证据](../eval/plango-product-next/README.md)已有真实门店原 run 的选优惠、修改、保存 v4 与实际重启记录，操作来自开发验证。[独立试用](独立试用验收.md)尚无真实使用者完成记录。冻结30例基线为 TSR 3/30、Groundedness 54.3%，不支持高可靠或强泛化主张，也不能被工程测试数量替代。

## 复杂度判断

Electron/WCV 同会话、LangGraph checkpoint、任务/版本/审批、输入接受事务、浏览器回执与 UNKNOWN、SSE 序号恢复，各有具体故障边界，应保留。无需更换框架、添加数据库、接 MCP 或增加 Agent 数量。

按优先级列出可收缩项；下列删行是审查估算，并未在本轮批量实施：

1. **先收敛共同语义路径。** `RequirementAgent` 与 `outcomes.price_fields` 分别解释人数和预算，是两处维护同一语言语义。自然语言与需求卡应最终使用有依据的稀疏修改；不能继续同步扩充两套关键词。当前质量优化开始修复共享契约，浏览器费用条件的窄规则解析仍是后续限制。
2. **delete：失效旧聊天通道。** `src/preload/index.ts` 的 `chat/confirm/onStep/onCard`、`src/main/ipc.ts` 的旧 handler/`projectedReply`，以及 store 的 `applyStep/addCard/clearCards` 已无主 UI 调用者；当前入口是 Harness。约50–70行及对应类型可删，历史持久数据兼容仍保留。
3. **delete：空社交通道。** SidePanel 的微信/飞书尚未接入；`imLoginQr` 返回空二维码，`imIncoming` 无生产者，`imSimulate/setSource` 无 handler，`proactiveTrigger` 永远拒绝。约25–40行及对应类型可删。已有分享、反馈与提醒保留，不为占位入口新接外部服务。
4. **shrink：重复子图声明。** `agent/subgraphs.py` 的 Input/State 字段可用现有 TypedDict 继承收缩，约60–100行潜力；必须保留输入边界、reducer、节点 ID 和 checkpoint namespace，直接抹掉子图收益不足以抵消升级风险。
5. **delete：未使用直接依赖。** Python `pgvector` 包无 import，实际向量功能使用原始 SQL；`opentelemetry-sdk` 没有 Provider/exporter 调用。可删这两个直接依赖，保留数据库 vector 扩展/迁移及现有 `opentelemetry-api`。不为解释依赖而新建 collector。

立即清理潜力约75–110行源码、2个直接依赖；子图另有60–100行。它们影响维护与展示清晰度，解决不了30例暴露的交付错误。本轮优先修共享语义与状态边界，避免清理工作抢走质量主线。

## 最小补证路径

共享机制修复 → 原集有界回归 → 冻结后独立来源组受控评测 → 修复版试用包 → 实际使用者沿现有任务独立操作。每一步保留同一 run、字段前后值、原来源、保存和恢复材料；已揭示案例只能叫回归。实际使用者验收尚未授权代发邀约，不以AI审查代替真实试用。

介绍项目时先讲上述一个闭环，再解释版本绑定、幂等恢复、事实范围与预算取舍。single/multi 是集中式工作流中的视角策略，不能介绍成自治团队或已证明多角色收益。
