# YOYU 闭环与设计成熟度评审

审查日期：2026-09-08；代码基线：`8834045`。本轮通过两组独立只读代码审查、内存规则探针及真实 Electron 地图检查形成判断，未修改产品逻辑或执行商户业务写入。

## 结论与证据范围

当前定位是可以运行和受控试用的工程 MVP。部署、命令执行、证据和恢复形成了技术闭环；部分读页面、算价格、展示与分享功能可以完成用户任务。连续商户操作、业务身份核验、地点变化后的重新检索和浏览器执行后的反思记忆仍有缺口，不能把这些能力统称为完整业务闭环。

之前的 47 个 Python 测试、23 项部署 API 检查、39 项 Chromium 断言以及菜单部署 smoke，证明对应回归和受控链路可用。它们未覆盖所有跨节点语义，也不是一般真实任务成功率。本次发现的问题与已有测试通过不矛盾，说明验收覆盖需要扩展。

新配置实测通过：实际应用读到重庆和非空 JS Key/安全密钥；在线 SDK 加载成功；“重庆解放碑”地理编码成功；诊断地图收到加载完成事件并实际绘制重庆底图。见 [检查结果](../eval/chongqing_map_check.json) 与[地图截图](assets/chongqing-map-check.png)。这验证配置与 SDK 基础能力，未验证完整行程路线、真实 GPS 精度、信息窗安全或商户交易。

| 闭环 | 当前证据与缺口 |
|---|---|
| 部署与运行 | YOYU 独立源码/配置、conda、Docker API/worker、PostgreSQL/Redis、健康和恢复已经实测 |
| 信息获取与结果展示 | 真实 DOM 读取、受支持表格与价格计算、来源展示及历史恢复已经实测；不代表复杂推荐全部可靠 |
| 连续业务执行 | 点击预约入口、填表、提交、身份回执核验尚未形成自动连续闭环；人工接管和确认回填可以补充结果 |
| 反馈与记忆 | 显式偏好、收藏和提醒 CRUD 可用；正常浏览器终态没有接回反思/记忆提案链 |
| 质量改进 | 有回归与失败保留；缺少代表性真实任务集、多次重复试验及专家分工收益对照 |

## 与成熟方法的对应关系

| 设计 | 合理部分 | 当前欠缺 |
|---|---|---|
| 浏览器观测和执行 | DOM 摘要、元素编号、任务/页面/快照绑定、隔离环境、操作回执都适合有界浏览器 Agent | 顶层 DOM 前 180 个目标、合成事件、全页失效判定，覆盖和可操作性明显弱于成熟浏览器驱动 |
| 本地 UI | Electron + React + Zustand、聊天/浏览器/成果分区、用户接管，适合桌面工作台 | 状态语义、定位来源、错误恢复、可访问性和不可信内容渲染仍需完善 |
| 规划 | 结构化需求、专家节点、确定性编译和校验、有界修复，适合边界明确的流程 | 约束的证据语义、刷新依赖、专家引用上下文存在实际错误 |
| 持久执行 | checkpoint、interrupt、幂等命令与 UNKNOWN 写结果是正确基础 | 持久化运行状态不能代替业务完成证明；副作用分类需要贯穿执行链 |
| 多角色分工 | 专家可以明确分工，确定性调度有利于预算和控制 | 当前没有自主派工；LLM 调用串行；多角色质量收益尚未测量 |

Electron [官方不建议继续依赖 `webview` 标签](https://www.electronjs.org/docs/latest/api/webview-tag)，提供 `WebContentsView` 等替代方向。这不否定当前真实浏览器实现，但意味着当前嵌入层不能称为官方长期优先方案。

这里需要区分框架与组件：Electron 本身是主流、成熟的跨平台桌面方案，[官方应用目录](https://www.electronjs.org/apps)包含 VS Code 等产品。YOYU 需要可见 Chromium、持久登录会话、Web UI 与本地控制能力，继续使用 Electron 合理；上述评价针对具体 `webview` 组件和实现，并非建议更换整个桌面技术栈。

### 浏览器执行路线补充：建议，尚未实施

建议保留 Electron 与现有 Harness，把执行层逐步接到成熟浏览器驱动，采用 DOM 优先、按需视觉观察和定位。当前沿用自研 DOM 桥是复用既有页面与登录态的过渡实现，不构成继续自研完整定位、等待和输入机制的理由。

- Playwright 提供较高层的 locator、自动等待、frame 和输入能力；CDP 是较底层的控制协议；截图/视觉是观测和目标定位方式。它们不处于同一层，可以组合使用。
- 先验证 Playwright 能否正确接管用户当前看到的 Electron 浏览页、session、导航和新标签。官方 `_electron` [仍为实验支持](https://playwright.dev/docs/api/class-electron)，[connectOverCDP 的支持完整度低于原生 Playwright 协议](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)。不能把 firstWindow 示例等同于所有内嵌 WebContentsView 的兼容证明。
- 可优先使用通过集成验证的 Playwright 能力；Electron 特有目标/输入缺口再通过主进程持有的 [Debugger/CDP](https://www.electronjs.org/docs/latest/api/debugger) 补足。UI、模型观测与驱动必须指向同一页面和浏览上下文。
- DOM 路径先使用语义定位、正确 frame、开放 Shadow DOM 和有界等待；canvas、图片型控件、缺失语义或仍有歧义的目标才进入截图定位。视觉确定目标后，能映射回 DOM 则仍走 DOM 定位，否则在校验截图尺寸、缩放、裁剪、时间和页面身份后执行坐标动作。
- 截图还可用于动作后观察，而不产生新点击。授权拒绝、登录/验证码接管、旧审批失效或提交结果未知，都不能通过切换视觉模式绕过；点击后超时可能发生在实际点击已经发出之后。
- DOM 与视觉共用同一命令 ID、审批、回执、重放限制和业务后验。更换驱动不会自动修复本报告中的 click 提前终止或业务身份校验缺口。

[Browser Use 的 `use_vision="auto"`](https://docs.browser-use.com/open-source/customize/agent/all-parameters)提供按需截图的实际先例；[Stagehand 的 Hybrid Agent](https://docs.stagehand.dev/v3/basics/agent)也组合 DOM 和视觉，其混合模式仍标为实验功能。这些支持路线可行性，不能代替 YOYU 自身的质量验证。

对普通表单与菜单，先完善 DOM 执行更有直接收益；对于面向复杂真实生活站点的长期目标，混合观测值得实施。应对同一批任务比较 DOM-only 与 hybrid，记录任务完成、误操作、接管、视觉触发/救回比例、延迟和用量，并独立验证所用模型的图像输入与定位能力。

Playwright 的[定位器](https://playwright.dev/docs/locators)、[可操作性检查](https://playwright.dev/docs/actionability)和[frame 支持](https://playwright.dev/docs/frames)可作为执行层可靠性的参照。DOM 编号仍可作为模型输入表示；底层执行可以采用更完整的定位、等待和输入机制。CDP 是控制协议，不是完整可靠性方案，Playwright [也说明 CDP 连接与原生协议存在保真度差别](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)。

Anthropic [区分预定义 workflow 与模型动态控制的 agent](https://www.anthropic.com/engineering/building-effective-agents)。本项目的固定阶段与程序校验是合理选择；没有理由为了名称而改成自由协商系统。LangGraph 的 [interrupt](https://docs.langchain.com/oss/python/langgraph/interrupts) 和 [persistence](https://docs.langchain.com/oss/python/langgraph/persistence)符合持久执行需要，业务边界仍须由应用正确实现。

## 优先问题

### 1. 高：忌口/过敏校验会把缺少证据当作满足

`vendor/planora/backend/planora/domain/planning.py:711` 将 `过敏:花生` 列为支持的约束，`:875` 附近只在店名/标签命中回避项时拒绝，缺少成分证据时没有补充 unknown。

独立内存探针给普通餐厅提供价格、营业与排队证据，但不给成分证据，结果仍为 `hard_constraints_pass=true`、`evidence_complete=true`、`executable=true`。浏览器比价路径已有未覆盖要求保护，行程路径没有复用同等语义。

改进：约束结果统一为满足、违反、未知；需要专门证据的条件不能通过“没有看到相反标签”认定满足。

### 2. 高：地图标题进入原始 HTML

来源链为 `src/renderer/src/lib/harnessProjection.ts:61` 的 `stop.name` → `PlanMap.tsx:33` 的标题 → `PlanMap.tsx:68` 的 `InfoWindow.content` HTML 拼接。高德[信息窗文档](https://lbs.amap.com/api/javascript-api-v2/guide/overlays/info-window)明确该字段接收 HTML。

宿主 CSP 允许内联内容，且 preload 暴露 `browserEval(code)`；`src/main/ipc.ts:48` 校验宿主与目标归属，未把原始脚本调用绑定到具体后端授权命令。因此宿主 HTML 注入可能获得超出模型命令契约的能力。

这是已确认的源码输入到 HTML 的风险链，未运行实际攻击或证明 SDK 利用。应先改为 `HTMLElement.textContent` 或正确转义，再把固定执行动作与授权核验收回主进程，缩小 renderer 的权限。

### 3. 高：普通 click 被混同为业务提交

`backend/yoyu/graph.py:379` 只把成功的 `type` 作为继续执行的底层交互；click 没有业务身份回执就进入 `PARTIAL_FAILED`。`backend/yoyu/receipts.py:189` 当前只生成 `page_confirmation`，而自动业务成功要求 `business_receipt + identity_verified`。

由此可见，缺口不只在支付：普通“点击预约入口 → 填表 → 提交”也无法由当前控制流自然连续完成。应按动作实际影响区分页面交互和外部提交，交互后继续观测；外部提交需要绑定具体业务参数的确认与后验核对。不确定结果仍保持 UNKNOWN，不自动重试。

### 4. 中高：重规划缺少结构化依赖刷新

`vendor/planora/backend/planora/agent/graph.py:336` 通过中文关键词决定是否刷新供给，需求解析后主要检查新增活动类型。以下输入的规则探针都返回 `False`：

- `改成重庆解放碑附近，其他不变`
- `从观音桥出发，其他不变`
- `改成明天，其他不变`

这确认了规则遗漏；复用旧地区/时段候选的下游影响是源码推断，尚未做完整真实任务复现。应比较新旧规范化需求中的地点、时间、人数和约束差异，明确使哪些候选、路线、价格和供给证据失效。

### 5. 中：多角色与记忆链不能按名称推断能力

`vendor/planora/backend/planora/agent/graph.py:1436` 的 Supervisor 采用 fallback，并记录 `constrained_phase_scheduler`。行程是阶段工作流加 LLM 专家。Advocate 通过 Send 形成逻辑分支，但共享的 `ModelAdapter` 在 `model_adapter.py:249` 对 structured 调用加锁，LLM 请求串行。

Advocate fan-out 输入缺少 evidence，worker 又按 evidence 校验报告引用，因此存在删除合法证据 ID 的路径。YOYU 在 `backend/yoyu/graph.py:598` 删除父图 execute→reflect，浏览器完成与回执节点直接 END。手动偏好 CRUD 可用，但不能据此声称浏览器执行结果会自动经过反思成为长期记忆。

改进：补齐真正需要的上下文与终态反馈连接；若要保留多角色，比较同一任务、模型与预算下单角色和多角色的质量/成本，再决定是否并发及保留哪些角色。

### 6. 中：UI 状态与定位标签存在可复现的不一致

`harnessProjection.ts:180` 把大写 FAILED/ERROR/TIMEOUT 以外事件全部标成 done。只读探针确认 `GRAPH_INTERRUPTED / WAITING_BROWSER` 和小写 `connection_error` 都显示成功状态，后者还丢弃 payload.message。StepFlow 因此把等待和连接异常画成绿勾。

`src/main/index.ts:67` 对宿主也使用商家域名的定位权限白名单，localhost/file 宿主原生 GPS 路径无法得到该权限；手填地址却在 `SettingsDrawer.tsx:141` 标为 GPS、精度 30 米，缺少观测依据。JS SDK 地理编码成功并不能证明真实设备 GPS 或该精度。

另外，BrowserPane 缺少加载失败/renderer 崩溃后的恢复 UI，手动 loadURL 未处理拒绝；标签切换与抽屉的键盘/焦点管理也不完整。应给运行状态、人工等待、部分结果、真实业务完成和错误分别建模，区分设备定位、手选地址、IP 与城市默认值。Microsoft 的[人机 AI 交互指南](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/)可作为能力边界、错误修复和用户控制的设计参照。

## 建议实施顺序

先修不可信内容渲染与约束证据判定，再完成普通页面交互到外部提交的连续控制流，并用规范化需求差分驱动重搜。随后完善 UI 状态/定位来源和浏览器终态反馈。浏览器执行层再按真实失败场景逐步补 frame、稳定定位、原生输入与目标范围的快照校验，规划迁移 WebContentsView；无需一次重写整个产品。

选择一个重庆场景作为完整验收：需求与硬约束 → 真实资料 → 方案 → 改商圈后重搜 → 多步页面操作 → 提交前核对 → 实际结果或明确人工确认 → 反馈记录 → 恢复。分别统计任务结果、错误完成、接管、重复副作用、延迟和用量。按 Anthropic [Agent 评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，评价实际环境结果，不能只看 Agent 的完成文字或轨迹绿勾。

本报告不主张已经覆盖全部文件、所有真实站点或所有安全风险，也没有把发现的问题写成已修复。地图配置已可用；业务与设计成熟度需要上述语义和真实任务证据继续补齐。
