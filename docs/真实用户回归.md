## 固定入口

[regression-cases.json](../eval/plango-next/regression-cases.json) 保留 9 个场景：重庆步行与同任务修改、人数/取消预算、准备恢复与审批失效、政府网页只读、用户图片，以及尚未验收的真实商家准备。每项包含原 run/数据位置、失败证据、期望、必要只读步骤和范围分类。其中 5 项是此前带范围的验收记录，1 项真实商家准备明确未验证；接续新增结构化卡同任务验证与真实扫码登录暂停。不是本次重跑了全部成功场景。

[inspect_trace.py](../scripts/inspect_trace.py) 只读取显式指定的 snapshot JSON，输出数值计数，不打印提示词、用户身份、完整 URL、模型配置或原始错误文本。`--check` 检查清单引用和 54 个归档事实，包括原失败金额、空天气、旧审批失效与累计用量；**通过只证明归档证据仍在，不证明当前产品或真实商家重新通过**。

```bash
python scripts/inspect_trace.py --check
python scripts/inspect_trace.py eval/plango-live-preparation/four-person-ready-to-review.json eval/plango-live-browser/external-read-success.json eval/plango-live-browser/image-upload-success.json
/home/song/miniconda3/envs/plango/bin/python -m pytest backend/tests/test_trace_regression.py backend/tests/test_current_spec_inputs.py -q
```

不同快照常属于同一个持久 run，不能把每个快照的累计 tokens 再相加。脚本保留 cumulative 和当前 turn baseline 两组数值；原样报告 fallback。没有对应 `identity_refresh_attempts` 字段的历史 Discovery 明确计入 missing，不按零调用解释。`cycle_flags` 是原历史标记数，不是已确认的模型循环次数。

## 本次实际修复

在 [Harness graph.py](../vendor/plango_harness/backend/plango_harness/agent/graph.py) 的两个共享函数收敛，不增加 Agent、模型调用、缓存层或追踪服务。

1. `_semantic_cycle` 先前从整个追加 trace 取最后 4 个 coordinator 动作。多轮正常的 `discover → advocate` 被拼成假循环；原准备 run 第 4 版人数编辑的第一条 coordinator 已带旧循环标记。现在从最近 `requirements_ready`、`replan_requested` 或 `clarification_received` 边界累计动作；原 trace 不修改，同一需求流程内真正重复仍会触发原保护。
2. `_advocate_roles` 先前仍用累积 `spec.goal` 选择角色。原任务已经取消预算，但历史中包括“预算”的文字仍触发预算 Advocate；此前去掉专业节点 prompt 中的旧 goal 没覆盖角色分派。现在分派只看当前约束、偏好、同行角色/非零计数和规范预算。当前明确低预算、便宜偏好、儿童等仍选择对应视角；历史角色和旧报告不删除。

[最小回归](../backend/tests/test_trace_regression.py) 直接读取原真实快照作为反例，另用明确受控的同轮循环验证保护仍在；同时检查当前预算/偏好/儿童分派、归档不变和统计脚本不输出提示词。既有 `test_current_spec_inputs.py` 验证真实编译的专业节点仍只使用本轮规范与报告。两项检查通过不等于重跑真实模型后已量化提速。

## 下一次有界复验的具体落点

- 单站锁定稳定后，先比较“仅改人数”的实际 trace。当前 Discovery 对全部 `place_candidates` 做过期身份刷新；可在已锁定唯一站点、没有其他必需活动的前提下，只向该站点派生事实和 Advocate 传当前相关候选/证据。必须保留强制目标核验、过期失败 unknown、日期天气及预算计数。此次不直接削减候选，避免破坏普通多站规划或绕过未知条件。
- 政府页重复读取先比完整 command/page-version/目标字段。当前 `read_outcome` 的 `page_read` 门槛只证明保存了可读文本；不能用 `status=satisfied` 直接跳过 Browser 决策，否则“继续打开某来源再读”的目标可能在中间页提前结束。应先把所需事实/来源和导航目标覆盖写入现有 Goal/后验，再做无新增事实的重复读收敛。
- 对当前两处窄修，先用同一冻结快照做离线回归；下次必要真实人数/预算编辑时记录新 source revision、同一 run 的累计和 baseline、实际角色数、请求数、身份刷新成功/失败以及用户等待范围。没有新对照前只报告代码/回归通过，不宣称节省百分比。

所有新验收必须使用归属明确的独立 profile/数据库，保留旧失败、checkpoint、审批、幂等与 UNKNOWN；默认 cap 不因失败上调。账号接管、准备待核对、真实预约/下单/支付/外部消息分别记录。原准备诊断的 60000 cap 不自动沿用到新场景。
