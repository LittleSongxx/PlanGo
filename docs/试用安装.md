# PlanGo Linux / WSLg 试用安装

本试用交付面向 Linux x86_64 与有图形桌面的 WSLg。桌面包含已经验证版本的 Electron、编译后的 React 和运行依赖；后端使用本包内源码构建 Docker 镜像。运行不需要源码仓库、Vite 开发服务器、Node/npm 或主机 conda。需要 Python 3.12+、Docker Engine + Compose v2、Linux Electron 系统动态库及可用图形会话；首次启动需要联网下载 Docker 基础镜像和 Python 锁定依赖。本包不是离线容器镜像或 Windows/macOS 安装器。

## 构建与全新安装

在本仓库已有开发环境执行（不会读取 `.env` 或用户 profile 进包）：

```bash
npm run package:trial -- release/plango-0.1.0-linux-x64.tar.gz
```

归档只包含明确列出的应用、后端、Skills、锁文件、原作者元数据、固定上游来源和 Electron/依赖许可证；`THIRD_PARTY_NOTICES.txt` 也包含编译进 React 界面的依赖声明，旁边生成 SHA256 文件。`trial-release.json` 记录 Git revision、源文件是否有未提交修改及完整应用内容摘要；用户未跟踪的融合方案不进入归档。版本号相同的后续测试包请使用不同文件名，保留旧包和失败记录。不要把冷备份与公开试用包混放或发送给他人。

接收者先核对可信来源的 SHA256，解压到临时目录，执行安装器；安装目标必须不存在：

```bash
sha256sum -c plango-0.1.0-linux-x64.tar.gz.sha256
mkdir plango-unpack
tar -xzf plango-0.1.0-linux-x64.tar.gz -C plango-unpack
python3 plango-unpack/scripts/trial.py install plango-0.1.0-linux-x64.tar.gz "$HOME/.local/share/plango-trial" --project plango-trial --port 18021
cd "$HOME/.local/share/plango-trial"
```

安装器生成仅当前用户可读的 `.env`，不复制开发者密钥。填写 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`、`AMAP_WEBSERVICE_KEY`；地图另需 `AMAP_JS_KEY` 与 `AMAP_JS_SECURITY`。默认城市重庆和默认预算不变。Docker 模型配置取自此 `.env`；桌面设置中的本地模型覆盖不会自动修改已运行 Docker 服务。

```bash
python3 scripts/trial.py doctor
./start.sh
./start.sh  # 复用归属已确认的桌面，不重复启动
./stop.sh   # 只停止此安装所属资源，保留三个数据卷
```

诊断只输出存在性、格式和权限的布尔值，包括 Docker Engine/Compose 可用性和 Electron 动态库，不输出密钥、URL、原始 Compose 配置，不调用模型或高德。缺少模型/高德时仍可启动桌面查看配置，相关业务不会伪造成功。日志位于安装目录 `output/lifecycle/`；日志属于私有诊断资料。桌面入口是包内 `electron/electron . --user-data-dir=...`，加载 `out/renderer/index.html`。启动器仅构建一次三项 Python 服务共用的 API 镜像，再以 `up --no-build` 启动，避免并行导出同一镜像标签的竞争。

安装身份在 `trial-install.json`。独立安装默认使用自己的 `profile/`、`plango-trial` Compose 项目与 `plango-trial_{postgres-data,redis-data,runtime-data}` 卷。不要改该文件来指向其他用户/项目资源。启动器核对实际进程、开始时间、cwd 和 Docker 标签，旧 PID/CDP 文件不代表活跃进程。

2026-09-09 的 D1/D2 源码更新增加可恢复发送与执行服务摘要；此前 revision=`a05f037` 的门店 UI 归档不包含这次更新。新版后端迁移至 `0013_input_acceptance`，保留原数据库并新增接受记录；桌面草稿、IndexedDB 图片附件和 Harness 输入回执均在原 profile 内，恢复时需要完整保留。后续D3–D6源码另增加优惠选用、独立距离字段和有限同城公交费用，旧门店UI包同样不包含。不要用清库或换 profile 处理发送失败。输入显示“已接收”时只取回原任务，“送达待核实”时先核对；显式重试复用原请求和内容指纹。

运行服务摘要来自连接的后端，桌面配置保存不会覆盖独立 Docker 环境。模型诊断是主动按钮触发的有界文本请求，可能产生少量用量；不验证图片、任务工具调用或独立 worker 当前配置。

## 冷备份与恢复

先处理当前人工接管/待审批任务，并确认无活跃租约、待用户命令或未回执浏览器命令；不要通过重新授权或重放 UNKNOWN 来消除待办。停止本安装后做冷备份：

```bash
./stop.sh
python3 scripts/trial.py backup "$HOME/plango-backups/trial-20260909"
```

备份拒绝活跃桌面、未确认的 profile 锁、运行中容器和被占用的卷；不会自动停其他资源。它保存 PostgreSQL 16、Redis 7（包含队列与 PEL）、runtime 的完整冷卷，以及完整 profile、桌面身份、UNKNOWN/幂等回执和私有 `.env`，附 SHA256 清单。目录权限 700、文件 600。备份不是脱敏材料，需保留原系统密钥环；跨机器解密 Cookie 不属于本次保证。

恢复只进入**另一个全新安装项目**，目的卷和 profile 必须从未创建，拒绝覆盖非空数据。先按上述安装流程用不同项目名/端口创建安装，尚不要启动；随后在新安装目录执行：

```bash
python3 scripts/trial.py restore "$HOME/plango-backups/trial-20260909"
```

恢复后原服务仍停止，所有业务行/队列/身份保持；仅新安装服务端口独立。恢复检查源文件校验和、PostgreSQL/Redis 主版本；失败保留部分目标供排查，不清理源备份。校验恢复数据后再启动；不要同时启动源与副本去执行同一真实业务任务。Chromium 的过时 Singleton 进程锁不会复制到新 profile，登录数据和业务回执不重置。

## 升级已有安装与接续当前项目

已有试用安装先停止，再显式选择新包与全新备份目录：

```bash
python3 scripts/trial.py upgrade /path/to/new-plango-linux-x64.tar.gz --backup "$HOME/plango-backups/before-upgrade-20260909"
./start.sh
```

升级先做完整冷备份，再替换应用文件；原 `.env`、`trial-install.json`、profile 和三个原卷原位保留，旧应用另存在备份 `application/`。备份、恢复和升级与启动器共用维护锁。文件替换失败会恢复旧应用；若回滚也失败或维护中系统退出，旧文件保留在安装目录旁的 `.plango-previous-*`，`trial-upgrade-in-progress.json` 记录位置并阻止启动，不能删除该记录后盲目启动。先根据记录恢复完整旧应用，或在独立目标恢复冷备份。

启动沿用现有 Alembic `upgrade head`，不清库或新建身份。平台或 Electron 版本改变会拒绝自动升级，须先通过浏览器兼容验证。数据库升级后不可仅换回旧程序冒充回滚；需要独立目标恢复完整冷备份。

当前源码部署 `plango` 也能接续到安装版本，无需复制/重命名数据库或 profile。该路径需要明确维护窗口：先确认原任务/租约/待命令，使用原仓库 `stop.sh` 停止并移除原容器（保留卷），再使用本安装器备份原仓库。以下是维护操作说明，本轮没有对主服务执行：

```bash
python3 scripts/trial.py backup /private/path/plango-before-install --root /absolute/path/to/PlanGo
python3 scripts/trial.py install /path/to/plango-linux-x64.tar.gz /absolute/path/to/plango-installed --project plango --reuse-backup /private/path/plango-before-install
```

安装器只接受原项目名，核验原三个卷归属、停用状态与 profile 锁；复制备份中私有配置，原 profile 路径和原 `plango_*` 卷继续使用。若旧目录容器仍存在、数据卷缺失或 profile 仍被占用，就拒绝接续。**不要同时重启原源码部署与新安装。** 原仓库、原 conda `plango`、历史证据和兄弟 Planora 均不修改；新安装运行不依赖它们。

## 验证范围

在开发仓库运行 `npm run test:trial`，覆盖归档路径限制、诊断不泄密、安装归属拒绝、升级替换失败/回滚再失败和 UNKNOWN 保留，使用临时目录及明确标注的受控数据。`python3 scripts/check_lifecycle.py` 覆盖启动器的归属、重复启动、失败收尾和保留卷契约。

2026-09-09 实际验证使用私有 `output/trial-check/`、独立 `plango-trial-check` / `plango-trial-restore-check`、端口 28011/28012：

- 干净安装生成独立私有配置，真实 Electron 加载编译后的 `file://.../out/renderer/index.html` 并连接健康 Docker 后端；重复 start 保持原主进程。未配置模型/高德，没有真实业务调用。
- 在原独立安装上执行应用升级，保留原卷和 profile；Alembic 在已有 head 上运行，未引入新的数据库 schema migration。
- 冷备份恢复到另一独立安装前后，72 个 profile 文件内容一致；恢复启动后 17 张表的全量行指纹、受控历史审批/checkpoint/累计用量、1 条 UNKNOWN 动作和 Redis 的 1 条 PEL 精确一致。真实 Chromium 创建的**受控测试 Cookie**和原桌面身份/UNKNOWN journal 在恢复重开后仍存在；不是商家登录验收。
- 恢复启动时使用拒绝调用宿主 `node/npm/conda/uv` 的 shim，仍成功启动。源与恢复副本测试后全部停止，三个卷和失败日志分别保留，没有操作主项目数据。
