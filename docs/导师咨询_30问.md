# 小悠（YOYU）· 导师咨询提纲（30 问）

这份提纲用于讨论产品取舍与后续验证，不涉及平台内部接口或非公开信息。当前实现见 [设计文档](设计文档_小悠.md)，证据与未通过案例见 [融合实现与质量验证](融合实现与质量验证.md)。

## 先交代现状

小悠是 Electron 本地生活工作台，结合用户打开的网页、高德服务与项目内 Python Harness，管理信息抽取、行程、价格比较、审批和恢复。

代码已接通浏览器观测与操作、后端任务状态、来源展示、方案版本选择、局域网分享、显式提醒及记忆读写。自动化证据主要来自受控网页；真实模型试测仍有失败项。不能据此宣称真实账号、任意平台下单或长期推荐效果已经验收。

没有保证三套方案、断网自动切模拟供给、模拟订单或微信 24 小时陪伴。Cookie 保存在桌面浏览器分区，但启用远程模型后，对话、相关记忆、网页片段和截图可能发送给该模型服务；服务模式下任务与记忆也存储在部署端。

## 一、定位与范围（1–6）

**1. 桌面浏览器形态解决了哪个足够强的需求？**

目前能把页面、对话和证据放在一起，操作沿用用户打开的浏览器会话。我倾向先验证“查清信息再决定”的价值。想请教：这是否足以让用户专门打开桌面应用？

**2. 应当继续独立工作台，还是先收窄成一个任务入口？**

独立形态能组织多种来源，也增加安装与登录成本。想请教：初期应优先验证哪一种入口，判断依据是什么？

**3. 提醒应解决什么具体问题？**

现在只有用户显式创建的持久提醒，没有自动关怀或微信推送。我倾向先验证出发与截止时间提醒。想请教：哪些提醒有明确价值，哪些容易打扰？

**4. 规划、菜单、比价、浏览器操作里应该先砍哪一块？**

功能入口较多，真实站点覆盖有限。想请教：以完成一个稳定任务为目标，最值得保留的最小组合是什么？

**5. 一句话介绍产品应强调什么？**

候选是“把网页信息整理成可核对的决策依据”或“让浏览器操作可以审批与恢复”。想请教：用户更容易感知哪一种价值，如何避免只讲技术机制？

**6. 如何表达与本地生活平台的关系？**

目前使用网页和已配置的公开服务能力，没有正式交易合作接入。我倾向定位为帮助用户整理信息、辅助操作的工具。想请教：这种分工有哪些实际机会？

## 二、场景与用户（7–12）

**7. 用户最痛的是找信息、核价格、选方案还是协调同行人？**

当前价格比较能对照原文和预算，但复杂条件未必能自动判定。想请教：应该围绕哪一步做首批用户访谈？

**8. 首批用户应聚焦哪一类？**

带娃、约会、陪长辈都对应不同约束，目前没有用户研究证明优先级。想请教：选人群时应先看频次、约束复杂度还是愿意付出的操作成本？

**9. 从看方案到实际行动，最应该量化哪个变化？**

已有方案分享和投票，但还没有证据证明它提高到店率。想请教：先测决策时间、意见收敛还是实际采用率更有意义？

**10. 提前规划和临时决策应优先哪种？**

即时页面信息可能变化，长期计划也需要重查。想请教：哪种场景更适合当前需要人工核对的能力边界？

**11. “附近发现”怎样才比已有地图更有价值？**

目前附近信息依赖真实高德查询，优惠来自近期已观测的网页。想请教：应加入哪些已证实需求，才值得保留独立发现入口？

**12. 给一套还是多套方案？**

当前候选数由供给和验证决定，替代重点是经济和就近。想请教：默认显示一套并解释警告，还是同时展示可行替代，更能减轻决策负担？

## 三、证据与数据质量（13–17）

**13. 评价可信度应如何验证？**

当前保留网页来源，没有已验证的水军识别或抗污染效果。想请教：在只能取得有限公开证据时，哪些信号可以客观呈现，哪些判断应暂缓？

**14. 未知信息应怎样展示？**

缺价、未知营业状态和无法核实的业务结果会保留未知。想请教：怎样让用户知道缺什么、下一步怎样补，而不是只看到失败？

**15. 菜品或商家比较应如何避免无证据评价？**

当前优先做有来源的价格计算，复杂饮食要求可能只部分完成。想请教：从客观条件比较扩展到推荐，需要增加哪些证据与纠错方式？

**16. 网页与 API 组合最该先测什么稳定性？**

当前供给来自高德和浏览器页面，网站结构、登录状态会影响读取。想请教：首批验收应按站点、页面类型、地区还是账号状态分组？

**17. 不同来源冲突时怎样支持决策？**

网页、地图和用户截图可能不同步。想请教：展示时间、原文和冲突是否足够，什么时候应要求用户再次核对？

## 四、执行与平台接入（18–22）

**18. 具体网站适配应该从哪个低风险任务开始？**

通用浏览器链已有审批和回执，真实取号、预约与交易仍需分别接入和验收。想请教：从只读信息扩展到实际操作，哪个任务最容易建立可靠完成标准？

**19. 哪些能力应等待官方接口？**

支付、履约和核销没有接通。我倾向优先做好需求、证据与人工确认。想请教：浏览器辅助和平台接口之间应怎样划分职责？

**20. 寻求合作前最该证明什么？**

目前有本地回归和小规模模型试测，没有用户规模或商业转化证据。想请教：应优先补稳定任务完成率、节省时间还是实际用户反馈？

**21. 哪种持续价值值得投入？**

记忆、工作流和证据透明都可能有用，但尚未证明用户会长期保留桌面工具。想请教：什么观测能区分一次性演示效果和持续需求？

**22. 审批粒度该如何测试？**

当前输入与点击要确认，审批绑定页面、快照和参数，变更后可能失效。想请教：哪些可逆动作适合放宽，哪些必须逐次确认，如何用用户测试量化摩擦？

## 五、隐私与信任（23–26）

**23. 第三方页面操作还需明确哪些使用规则？**

登录与验证码交给用户，页面内容作为数据而非权限来源。想请教：面向真实用户前，应怎样核对平台规则、授权范围和账号风险？

**24. “本地优先”应怎样准确传达？**

Cookie 留在本机；远程模型会接收任务所需内容；服务部署的数据存储位置也不同。想请教：怎样在配置界面清楚展示这些数据流，让用户作出知情选择？

**25. 记忆的采集与纠错还应补什么？**

后端支持偏好、收藏和摘要，界面可查看、删除，首启不会生成虚构资料。想请教：自动提取、用户确认和默认不记录之间如何取舍？

**26. 家庭信息应怎样最小化？**

亲子规划可能涉及年龄与位置。想请教：哪些信息只需在单次任务使用，哪些确有长期保存价值，应如何向用户解释？

## 六、架构与验收（27–30）

**27. 什么证据表明需要更多 Agent？**

当前在线决策由统一 Python Harness 管理，尚无依据证明餐饮、调研等独立子 Agent 更好。我倾向先让现有流程稳定。想请教：哪些瓶颈值得引入并行分工？

**28. 现场失败怎样呈现才有信息价值？**

模型不可用、页面受限或价格缺失会显式报告；本地样本必须声明身份，不能用模拟交易补齐结果。想请教：三分钟演示里应预留多少时间展示恢复或失败原因？

**29. 怎样证明记忆改善推荐？**

目前没有长期效果试验。想请教：是否可以先对比开启/关闭记忆的任务表现，同时记录用户纠正次数和不希望被记住的内容？

**30. 下一轮验收只做三件事，该选什么？**

我的倾向是：一组真实页面的信息抽取与价格任务、一组审批后中断恢复、一轮小规模真实用户使用。想请教：这个顺序是否合理，每项的最低可接受结果应如何定义？

会后只把确认过的需求与验证计划写入路线图；咨询中的假设不直接改成“已经完成”的产品描述。
