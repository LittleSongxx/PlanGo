# PlanGo 面向 AI 应用开发岗位的项目评估

评估日期：2026-09-10。完整阅读根目录 1185 行面试知识图谱，核对架构决策、最新交接、生产调用链、工程检查和三组质量证据，并联网抽查相关岗位、原始面经及官方技术文档。三个独立子任务分别审查后端、桌面与基础设施、质量证据；主任务汇总并核对关键源码。阅读结束时仓库 HEAD 为 `5fd313e`，最新质量结果绑定产品提交 `53d4ef5`，二者不能混为同一评测版本。

**结论：PlanGo 可以用于投递 AI 应用／Agent 开发岗位，有实质工程内容；但当前工程完整性明显领先于业务交付可靠性。存在局部过度设计和旧产品遗留，最需要处理的是重复的语义解释及过窄的结果生成路径。继续增加框架、Agent 数量或业务入口，收益低于修通现有主线。**

本报告排除面试题、课程、导师提纲、教学图示及历史方案的篇幅，不因文档多、保留上游源码或测试使用受控样本而判定过度设计。以下问题均落在实际生产调用路径或仍打入产品的遗留入口。未修改产品、启动应用、调用项目模型／高德、重跑商家业务或提交代码；仅生成本报告及新的离线复算结果。

## 项目的实际定位

当前最清晰的产品目标是：用户选择门店和优惠，在同一任务里修改人数、日期和预算，查看来源与适用性，保存草案，中断后继续。可解释为“带真实浏览器、证据约束和持久恢复的本地生活决策助手”。

生产结构是 Electron／React 工作台，经 IPC 和 HarnessClient 进入 FastAPI／DesktopRuntime，再由 LangGraph 集中编排需求、检索、方案、校验和审批；页面操作走有界 ReAct，经主进程的 WebContentsView＋Playwright/CDP 操作同一可见会话。PostgreSQL 保存服务模式任务等数据，Redis 调度；本地模式使用 SQLite。模型专业节点共享适配器，`single/multi` 是视角策略。

这已超出单轮聊天封装，具有面试可展开的故障处理深度。需要进一步证明的业务价值是：在用户自己的条件和新资料下，是否比手动查页面、计算和保存更省事。目前不能由架构或开发演示推断真实用户采用、时间节省或成熟商家履约。

依据：[架构决策](架构决策.md)、[实际架构](Agent架构与选型.md)、[桌面任务入口](../src/main/harness.ts)、[后端工作流](../backend/plango/graph.py)、[开发验证](../eval/plango-product-next/README.md)。

知识图谱覆盖 18 章，混合 AI 应用、Agent、AI 全栈、算法与 Java 后端；它适合检查知识和追问深度，不能直接转换成一个项目的功能需求。H1／H2／H3 是该资料自己的面经证据分级，不是岗位覆盖率或录用概率。本次核查与 PlanGo 判断相关的部分，没有重新逐条认证所有原帖与频率标签。

百度公开校招“大模型研发工程师 J100834”强调 Python、模型 API、业务集成、RAG／Agent 及响应速度与稳定性，容器化是加分项。这支持以端到端工程和效果改进组织项目，而不能推出每个项目必须同时实现全部技术。[百度岗位原页](https://talent.baidu.com/jobs/detail/GRADUATE/7952a5bc-816a-4b9b-bd58-65d70a66d5d0)

另一公开“Coding Agent 策略算法实习生 J96208”强调任务拆解、工具选择、上下文、错误恢复、数据分析与对照实验，同时允许 Python、C++、Java、Go 等语言。它更偏策略算法，不能与所有应用岗混为一谈，但说明“能分析行为并验证改进”本身有岗位价值。[百度岗位原页](https://talent.baidu.com/jobs/detail/INTERN/a77dfe3a-0f3a-45b5-95dc-c7478f9d43e4)

抽查知识图谱引用的小红书／百度联合面经，原文确有“为何拆子图”“节点输入输出与上下文如何传递”“跑偏怎样处理”等问题，同时问数据库基础。由此得到的项目要求是能解释取舍及真实调用，不是增加子图数量。公开面经属于当事人自述，不等于企业统一面试标准。[原始面经](https://api-cdn.nowcoder.com/feed/main/detail/e319aadc79a9479397a6661a7f5ca088?sourceSSR=subject)

| 知识图谱主题 | PlanGo 现有项目证据 | 判断与补足方向 |
| --- | --- | --- |
| 业务目标、调用链、个人贡献 | 产品主线、生产入口、固定上游快照、评测失败可追溯 | 有基础；补真实用户价值和可解释的个人改动，不能把 vendor 全算原创 |
| Agent／Workflow、工具调用 | 集中式 LangGraph＋页面内有界 ReAct、类型化工具和预算 | 方向契合；应证明任务完成，不应靠角色名称增加分量 |
| 中断、审批、幂等与副作用 | 请求身份、版本审批、持久回执、UNKNOWN、恢复投影 | 当前最扎实的工程亮点之一 |
| 结构化输出、意图、多轮状态 | TaskIntent、field_evidence、TripSpec、需求卡 | 有机制但自然表达可靠性不足，是首要修复项 |
| 事实、评测、成本 | 来源绑定、TSR／Groundedness、Token 与失败保留 | 评测诚实度较好；结果仍低，AI 审核也出现过语义错标 |
| 上下文与长期记忆 | 显式偏好、经历、删除、有效期及可选 embedding | 可讲记忆边界；不能据此声称企业知识库 RAG 已完成 |
| RAG、混合检索、重排、文档 ACL | 当前核心是实时页面和类型化位置接口，非完整文档检索产品 | RAG 重岗位有证据缺口；先按目标 JD 判断，不能为凑关键词强塞 |
| 全栈与发布 | React、IPC、SSE、服务部署、安装／冷备恢复、CI | 有实现；缺当前修复版独立试用及服务部署形态的持续自动验证 |
| Java／Spring／JVM | 生产主体是 TypeScript＋Python | 不构成 Java 实践证明；通用后端概念可迁移，语言专项不能由 PlanGo 替代 |
| 模型训练、LoRA、RL、量化推理 | 当前以模型调用与应用控制为主 | 不属于当前产品必须补的功能；算法／训练岗另需相应项目证据 |

因此，面向 Python／TypeScript 的 AI 应用、Agent 工程岗位，项目方向匹配；面向 Java AI 后端、企业 RAG 或模型算法岗位，匹配具有条件。这里只评估项目证据，不推断候选人的个人掌握程度或具体录用概率。

## 哪些复杂度值得保留

| 机制 | 对应的实际问题 | 评估 |
| --- | --- | --- |
| Electron＋WebContentsView | 用户、模型、执行器看到同一登录会话，支持人工接管 | 产品需求直接成立；不建议换桌面框架 |
| Playwright＋受控 CDP | 在已有 Electron 页面执行语义定位，并处理适配缺口 | 不是两套独立浏览器；能力仍需版本适配验证 |
| LangGraph checkpoint＋业务状态 | 图恢复点、已接受输入和产品投影有不同提交窗口 | 状态职责不同，不宜简单合表或全部塞进 checkpoint |
| 审批、命令指纹、持久回执、UNKNOWN | 避免需求变化后旧授权继续生效，避免未知写入被重复执行 | 属于必要正确性边界，不能为缩短代码删除 |
| SSE 序号与恢复投影 | 断线后追平同一任务，避免重复显示或丢历史 | 有实际调用和测试，保留 |
| PostgreSQL＋Redis 服务模式、本地 SQLite 模式 | 持久任务与后台 worker，以及独立本地运行／隔离验证 | 有运维成本，但不是无依据的中间件堆砌；优先收敛默认使用入口 |
| 显式记忆、来源、有效期与删除 | 保留用户明确偏好，避免临时结果成为永久事实 | 适度合理；没有证据支持继续扩建复杂记忆体系 |

调用证据：`src/main/browserView.ts:158`、`browserDriver.ts:273` 和 `:295` 连接既有会话；`browser-bridge.ts:73` 绑定任务／页面；`harnessClient.ts:488` 在动作前保留回执，`:506` 处理回执重传。`vendor/plango_harness/backend/plango_harness/runtime.py:725` 起处理输入接受、checkpoint 和事件投影的不同崩溃窗口。`backend/tests/test_input_acceptance.py`、`test_receipt_atomicity.py`有对应检查。

官方 LangGraph 文档说明恢复可能从节点开头重新执行，因此 checkpoint 不能自动替代应用对副作用的幂等处理。Playwright 也明确提示 CDP 连接的兼容能力低于原生 Playwright 协议。这些资料支持保留 PlanGo 的恢复契约及适配验证，而不是假定接入库后问题自然消失。[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Playwright connectOverCDP](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)

## 真正需要收敛的生产复杂度

**最高优先级：同一语言语义被不同路径重新解释。**

规划修改由 RequirementAgent 产生结构化补丁；浏览器上下文仍无条件调用另一套 `price_fields()` 正则解释人数和预算。即使 TaskIntent 正确，后续旁路仍可漏改或误改。位置：`backend/plango/graph.py:205`、`:218` → `outcomes.py:548` → `price_fields:559`。

本次仅内存纯函数检查，固定旧 reasoning 任务为 2 人／总预算 180，显式传入正确的 `TaskIntent(kind="continue")`：

| 新输入 | 实际结果 | 应有语义 |
| --- | --- | --- |
| 人数改为4人 | 4人 | 4人 |
| 参与者改为四位成人 | 仍2人 | 4人 |
| 人数不要改为4人，其余不变 | 错改4人 | 保留2人 |
| 不设预算 | 仍保留180 | 清除预算 |

这是生产函数的工程反例，不是一次新的模型评测或总体成功率。应让语义理解产出统一的、有出处的稀疏修改，再由代码校验类型、单位、否定／清除冲突、版本及落库。不要继续同步扩充两份关键词表，也不要把问题解释成单纯提示词不够长。

**同样高优先级：资料分析承诺的范围大于结果路径实际支持的范围。**

`graph.py:722` 让模型只抽取 SourceAnalysis 字段；`outcomes.py:794` 的结构集中于单套餐、餐费、票价。`:850` 遇多文档或多优惠直接返回空；`:855` 起再用少数中文模板验数字；`:906`、`:923` 主要只有“餐费＋交通”和“单套餐适用性”两支，其他情况在`:976`返回空。

纯函数反例中，资料其余部分、引用和结构化提取都正确，仅把“每份套餐售价136元”换成“每份售价136元”，结果就由可形成核算变为 `None`。这说明问题不完全来自模型抽取，可信数字还受额外话术模板限制。

应保留来源核验、费用口径、确定性验算与未知表达；把现有结果路径收敛为必要的费用项目、对象、单位、条件和推导关系，能对来源齐备的问题形成结论。不能简单删除防护让模型自报总价，也无需建设通用规则引擎、第二事实库或再加一个 Agent。

**中优先级：多视角的默认成本尚无收益证据。**

`docker-compose.yml:10` 默认 `multi`；工作流按条件增加 Advocate 视角，但 `agent/model_adapter.py:99` 的锁会串行化同一 run 的模型调用以保护预算。多角色不等于并行提速，更不等于自治团队。串行锁本身是可解释的简化，问题在于额外视角是否值得成本尚未证明。

当前先冻结角色扩展；核心交付修复后，如要保留“多视角改善效果”的卖点，再用同条件、小范围对照比较 TSR、G、Token 和用时。没有收益便选择更简单策略。遵守现有大规模角色评测暂停约束，不因本报告自动开启 sweep。Anthropic 的工程经验同样主张按可验证效果增加复杂度；其多 Agent 研究实践不能直接证明 PlanGo 的多人行程需要同样结构。[简单模式原则](https://www.anthropic.com/engineering/building-effective-agents)、[多 Agent 系统实践](https://www.anthropic.com/engineering/multi-agent-research-system)

**低优先级：确认可收缩的旧产品代码和依赖。**

| 项目 | 实际依据 | 最小处理方向 |
| --- | --- | --- |
| 旧聊天 IPC | `src/main/ipc.ts:170`旧入口包装 Harness，`:174`旧确认恒报失效；正常 UI 已走 `store.ts:413` | 清旧接口及未用投影，保留持久数据兼容 |
| 微信／飞书占位入口 | `ipc.ts:195`返回未接入，`SidePanel.tsx:38`仍展示页签，`App.tsx:40`订阅无生产者事件 | 删除或隐藏空壳；不为填空新接社交平台 |
| 旧卡片生产链 | `OutcomeCanvas.tsx:105`等仍渲染 deal／takeout／queue／consensus／旧discover；当前 `projectHarness`不生产这些类型，`addCard`无调用 | 清理死分支；保留真正使用的 DiscoverPanel 和 OfferComparisonCard |
| 未用 Python 直接依赖 | `pyproject.toml:24`的pgvector包无import，向量查询使用SQL；`:26`的OTel SDK无Provider/exporter | 可删两个直接依赖；不删除数据库vector扩展、迁移及OTel API |

这些属于产品遗留，不是教学内容；但不能靠删掉它们解决 TSR。重复 TypedDict／子图字段也有局部收缩空间，不过子图真用于生产，改动涉及 reducer 和恢复兼容，收益不足以优先处理。不提供未经实施验证的精确总删行数。

## 当前最影响投递说服力的缺口

**第一，核心业务结果尚未可靠交付。** 本次使用独立 `plango` Python 串行执行原聚合器，对三个最终审核包离线复算，均 `complete`、`issues=[]`、N/A=0：

| 被测产品／数据 | TSR | Groundedness任务宏平均 | 支持事实／事实总数 |
| --- | --- | --- | --- |
| de37fecd／原30题 | 3/30，10.0% | 54.29% | 384/541 |
| 53d4ef5／旧六题回归 | 0/6，0.0% | 91.18% | 105/116 |
| 53d4ef5／冻结后独立六题新资料 | 1/6，16.7% | 82.08% | 163/167 |

原30题来自15组虚构受控来源，20题观测注入＋10题Electron状态流程；本轮两组六题各4题观测注入＋2题Electron。独立新资料指冻结后另行编写的来源组，不是真实新网站采集。

复算结果：[派生输出目录](../output/audit-score-CYK2Fs/)。这是格式、引用定位和统计复算，不是重新运行 Actor，也不证明 AI 审核的语义绝对正确。各组任务不同，不能跨组相减声称总体质量提升；六新题现已揭示，后续也只能算回归。

新集唯一成功是保存恢复。FRESH-02 的37条事实均有支持，但未形成选券、283元实付及17元余量；FRESH-04的32条事实均有支持，却未完成路线长度、超限和到达时间等核算；FRESH-06也未完成所需适用性及开销判断。准确摘录能提高G，不能代替用户请求的最终答案。参见[新集最终报告](../eval/quality-v3-independent-six/README.md)及其[逐项审核](../eval/quality-v3-independent-six/review/output-review.json)。

尤其应避免两个错误归因：NEW-18的运输恢复、19:20／120分钟修改已通过，失败在未交付草案；FRESH-03的4人／人均115元／90分钟已经写入，独立总预算字段为空仍能表达460元有效上限，不能称“预算丢失”。后者已修正一条AI事实错标，G由81.67%改为82.08%，缺草案导致的TSR失败不变。评测金标也需接受等价业务状态，而不是要求冗余字段长成指定形状。[正式更正记录](../eval/quality-v3-independent-six/independent-output-review-v3-change-log.json)

**第二，测试数量与模型质量之间的证据仍有断层。** 冻结产品有489项pytest＋87个子检查及类型／构建记录，但例如`test_requirement_grounding.py:31`由AsyncMock提供正确提案，`test_task_intent.py:56`直接传入正确意图。它们合理地检查机制，不能证明真实模型稳定理解用户。保留现有测试，在共同语义、交付终态及新来源任务上补有效反例即可，不需要再造评测平台。[工程记录](../eval/plango-quality-v3/engineering.json)

当前全部语义审核来自独立上下文AI，人工0，不是跨模型家族或真实网站第三方盲测。已有冻结、失败保留、invalid裁定和版本绑定可以作为评测工程亮点；之后补少量真实使用者判断有价值，无须现在为每轮开发重新索要人工签名。官方 Agent 评测实践同样区分运行轨迹与环境最终结果，并指出模型评分需要校准。[Anthropic Agent 评测](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**第三，长期资源边界仍有实际缺口。** `src/main/browser-bridge.ts:7`的全局commands Map保留每条命令的完整结果Promise，`:120`持续写入；`:30`释放任务时不清这个Map。观察可能包含网页正文、表格和截图。现有持久回执有上限，不能替代该内存层的清理。应按已确认回执和任务生命周期释放大结果，同时保留防重放身份与UNKNOWN保护；不能简单超时删除后允许旧动作重做。这是源码可见的保留风险，本次没有进行堆分析，不能认定它就是WSL崩溃根因。

**第四，Electron 内核维护应在下一次试用发布前处理。** 锁文件实际版本为`33.4.11`（`package-lock.json:2387`）。Electron官方v36发布说明明确33系列已经停止支持。因为它承载真实网页，版本维护不是为了追新框架；应升级至届时受支持版本，并复验同会话、CDP、弹窗、登录、审批、回执和打包。[Electron停止支持说明](https://releases.electronjs.org/release/v36.0.0)、[官方支持政策](https://www.electronjs.org/docs/latest/tutorial/electron-timelines)

**第五，部署、观测和独立使用需要最后一段证据。** CI 已覆盖类型、后端、迁移和真实Electron受控测试；但`.github/workflows/checks.yml:39`的默认full-stack走`desktop/local://`，没有自动运行PostgreSQL＋Redis＋API＋worker的service模式。已有手动deployed入口，因此应复用它补一条隔离服务模式的队列／恢复检查，不需要Kubernetes或另一套平台。

已有模型用量、延迟、事件和span接口，尚无配置完成的OTel exporter／collector；不能声称全链路观测平台。优先用现有事件关联一条任务的模型、工具、等待和恢复耗时，连同Token解释失败及成本，保留TSR与G两个主指标。样本太少时不应包装稳定P95或成本优势。

试用包仍绑定`a308b20`，与最新质量修复版不同；[独立试用验收](独立试用验收.md)尚缺真实使用者完成记录。主线可靠后更新一个目标环境的试用包，让一位未参与开发的人用自己的地点与条件完成读取／比较／编辑／保存／恢复，记录卡点。无需先补齐预约、支付、微信消息或所有桌面平台。

## 不应为了投递而新增的东西

| 候选扩展 | 当前判断 | 何时才值得加 |
| --- | --- | --- |
| MCP／A2A | 不解决已发现的语义和交付问题 | 确有多个外部客户端需要复用工具或跨Agent系统互操作 |
| 企业文档RAG、混合检索、Rerank | 当前网页与位置数据主线没有自动导出此需求 | 真实持久文档量、检索遗漏或目标岗位要求给出明确收益 |
| Java网关／Spring服务 | 增加跨语言调用与部署成本，不能自动证明Java能力 | 真有Java业务服务需要集成；否则由另一段实际项目覆盖 |
| 微调／自部署推理 | 当前已证明部分错误存在于确定性代码，即使正确提取也会失败 | 应用契约修好后，仍有足够数据证明基础模型瓶颈 |
| 更多Agent、记忆框架、通用规则引擎 | 扩大维护范围，缺少效果依据 | 简单实现经对照确实不够 |
| 支付、锁位、外部消息、全商家适配 | 超出现有可验证主线，还引入真实副作用 | 产品定位明确需要，取得授权并具备相应接口与验收条件 |

MCP官方限定自身为上下文交换协议，不规定应用如何使用LLM或管理上下文。因此“没有MCP”可以是某个岗位的经验缺口，却不是PlanGo当前设计不完整的证据；本项目保留直接类型化适配器有合理理由。[MCP官方架构](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)

## 建议的最小完成顺序

1. 修统一稀疏修改与资料交付路径。能正确处理否定、同义表达、清除、其余不变；已有充分资料时形成所需答案或草案，仅为当前目标真正缺失的信息澄清。保持权限、来源、预算和恢复不变量。
2. 用少量共同机制反例及已揭示资料做有界回归，保留原失败；再冻结修复版，独立按来源组验证。验业务等价约束和最终可见交付，不验某个冗余字段或指定措辞，不为追分改金标或扩预算。
3. 修命令结果生命周期，升级受支持Electron并复验浏览器适配；沿现有入口补服务模式持续检查。避免把长期稳定或性能改进说成已经证明。
4. 更新试用包，补一条真实使用者独立完成主线的记录，并用现有日志说明一次正常任务和一次失败恢复的耗时与Token。测试内容和真实商家事实继续明确区分。
5. 顺手清旧IPC、空社交入口、死卡片和两个无用依赖；保持角色扩展、交易支线和新框架暂停。

用于投递时，可以主讲“真实可见浏览器＋版本化计划＋审批及幂等恢复＋可追溯评测”。应能沿一次请求解释具体代码，展示固定上游与自己改动的边界：[上游快照](../vendor/plango_harness/SNAPSHOT.json)。当前不能主张高成功率、自治多Agent收益、成熟RAG平台、长期稳定或真实预约履约。

项目继续投入的价值取决于能否把已有工程机制转化为用户真正拿得到的结果。最有说服力的下一项成果，是修复一个共同机制、保留可复验的前后证据，并让普通用户独立完成现有主线。
