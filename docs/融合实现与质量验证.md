# YOYU 融合实现与质量验证

日期：2026-09-08。实现分支：`feat/planora-browser-harness`。

## 最终边界

YOYU 自己拥有 Electron 界面、浏览器会话、Python 环境、配置、数据库、检查点、命令回执和服务入口。`vendor/planora` 是项目内可修改的固定源码，不是指向另一个仓库的依赖。删除或继续修改原 Planora 仓库不会改变 YOYU 的运行代码。

来源固定在 v7 公开归档；基线归档 SHA-256 为 `5e5c873687e4a783ca9e1520704ea852c9b99fdad60646288678f80c24f41953`。逐文件来源见 `vendor/planora/SNAPSHOT.json`，三方合并基线见 `vendor/planora/upstream-base.tar.gz`。后续只通过显式只读检查了解上游变化，不自动追随测评中的工作区。

按照用户授权，从 Planora 复制所需模型与高德 Web 服务配置到 YOYU 自己的 `.env`；文件权限为 0600、被 Git 忽略。运行时只读取 YOYU 配置。模型统一通过 OpenAI-compatible 接口使用。高德 JavaScript 地图 Key 和安全码仍需单独配置。

## 保留与融合

| 层 | 当前职责 |
|---|---|
| YOYU 产品界面 | 聊天、内置浏览器、行程画布、地图、菜单与优惠、来源、审批、历史、分享、提醒 |
| Electron 主进程 | 启动自有后端、认证和事件传输；持久化命令回执；校验真实浏览器操作边界 |
| Python Harness | 任务轮次、需求、候选、编译、验证、预算、审批、检查点、恢复、记忆和 Skill |
| Browser Provider | 从当前真实网页提取事实；导航、滚动、输入、点击；无页面证据则保留未知 |
| 外部接口 | 可配置的兼容模型端点、高德地点与路线服务；账号登录由实际网页完成 |

默认 SQLite 与本地消费者足够运行桌面应用；可选 PostgreSQL/Redis Compose 使用 YOYU 专属配置及数据卷。没有为融合引入跨仓库 RPC 或第二套在线 Agent 决策循环。

## 调研如何落实到代码

1. **用任务结果评价 Agent。** Anthropic 的 [Agent 评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)强调环境结果与过程轨迹的区别。因此“模型说 finish”“页面读取成功”都不能单独证明比较、推荐或业务操作成功。YOYU 用有来源的结果产物、金额计算和最终状态共同验收，并把能力用例与已发现问题的回归分开记录。
2. **恢复必须考虑副作用。** [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) 和 [persistence](https://docs.langchain.com/oss/python/langgraph/persistence)描述了中断恢复时节点重放的语义。YOYU 在执行前持久化命令状态，保存实际回执；中断后不确定的写操作保持 UNKNOWN，同一命令改变参数会被拒绝，避免恢复时重复提交。
3. **让工程代码承担可精确验证的步骤。** [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)支持优先采用可理解、可组合的流程。模型负责抽取和下一步选择；价格乘人数、预算比较、方案锁定和来源核验由代码处理，无需再加一个评分 Agent。
4. **兼容接口仍需验证结构与错误。** [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)和 [Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)提供结构化输出与工具契约。第三方兼容端点的支持范围并不必然一致。这里保留本地 schema 校验、最多一次有界修复、实际 usage 计费与额度错误快速停止；不通过提高预算掩盖结构失败。

## 本次发现的问题与优化

| 问题 | 根因与修改 | 验证位置 |
|---|---|---|
| 看完帮助页就宣称完成餐厅比较 | 完成状态曾依赖模型 finish；现在要求可展示、带来源、可核算的比较产物 | `backend/tests/test_task_quality.py` |
| “总预算改为150”丢失浏览器任务 | 单轮意图路由丢掉原始目标；持久化任务模式、原始要求和后续修改，重新观测当前页面 | 同上 |
| 总预算与人均预算互相清空 | 稀疏修改误当完整替换；独立更新每个明确字段 | 同上、`test_plan_alternatives.py` |
| 邻店价格、队列或推荐卡被归给目标 | 全页命中引文不等于同一实体；按实体区块校验字段归属，禁用旧抽取缓存 | `test_entity_grounding.py`、`test_price_grounding.py` |
| 教学示例成为真实价格 | 指令性文档和示例未与商家事实区分；保留原文但拒绝作为报价 | `test_task_quality.py` |
| 未知营业/排队信息被当成关闭或零等待 | 缺失与否定事实混用；缺失字段保留 null、独立标注证据不足 | `test_live_supply_contract.py` |
| 最便宜候选无效后错过可行替代 | 替代编译过早停止；在现有预算内尝试有界候选，经完整编译验证，保留锁定身份与时间 | `test_plan_alternatives.py` |
| 比较了未被用户要求的商家 | 观测池直接替代目标集合；以请求中的商家或明确的当前页面范围筛选 | `test_comparison_scope.py` |
| 忽略人均上限、忌口、人数撤回 | 未识别的条件被默认为满足；只认领已核验的要求，未覆盖条件保留 partial，并抑制最终推荐 | `test_comparison_constraints.py` |
| 图片或算价入口绕过结果核验 | OCR 入口和多处关键词判断各自宣称成功；统一使用任务上下文，截图识别不能冒充比较完成，算总价请求必须交付算价产物 | `test_outcome_entrypoints.py` |
| 点按钮后显示业务成功 | 浏览器交互回执与业务履约混用；分开记录页面步骤、页面确认与用户核实 | `test_receipts.py`、UI 投影检查 |
| 页面变更或命令恢复重复执行 | 审批绑定真实页面/快照/参数，隔离世界保存快照；回执在本地持久化，跨轮次与取消有独立状态 | `scripts/browser-regression.cjs`、`check-harness-transport.ts` |

比较功能目前只自动完成有充分证据的人均价格与预算比较。复杂饮食、营业条件、任意多目标推荐等尚未有完整验证器；这些条件不会因为价格表存在就被判定满足。这是已知能力范围，不是“所有自然语言要求均已实现”。

## 证据分组

- 固定离线问题基线 12 个语义场景：最初 4 通过、8 失败；保留原始 `eval/task_quality_baseline.json`，后续结果见 `eval/task_quality_results.json`。
- 单独的正向对照要求真正交付结果：两个商家人均 68/82、3 人、总预算 240，必须得到 204/246、预算判断、差额 42、推荐及来源。不能靠全部拒绝提高回归通过率。
- 后续发现的商家范围、自然预算表达和未知约束问题单列，不能偷偷扩大原基线分母。
- Electron 原生检查实际执行 Chromium DOM 操作；desktop 使用明确标记的协议测试后端，full-stack 使用真实 YOYU Python 后端。这些网页均为本地受控样本。
- 独立启动检查把公开源码和锁文件复制到另一临时目录，离线创建自己的环境，并注入无关上游环境变量，验证不会连接或读取原项目。
- 真实服务连通性：`eval/live_service_20260908T114926Z_658eb729.json` 记录 1 次模型请求、186 tokens、约 3.39 秒，结构与引用检查通过；1 次上海高德地理编码约 184 毫秒。它只证明接口可用与这个极小抽取契约。
- 真实模型任务试测使用固定 4 个场景、5 个轮次的合成 DOM，源码和用例哈希冻结。每场景最多 4 次模型请求、批次最多 16 次；不批准写操作，不访问真实商家站点。默认预检不发请求：`.venv/bin/python scripts/check_live_task_quality.py`；核对其输出哈希后加 `--run --source-sha <hash>` 执行。

### 真实模型第一批的失败证据

`eval/live_task_quality_20260908T122128Z_55b4bfa7.json`：4 场景中 3 个达到预期；正向任务 1/2，防误判负例 2/2。多轮案例第一轮正确，第二轮已重新观测到 99/69 的人均价格，但未交付结果就触及预注册的每场景 4 请求上限，因此整个多轮案例记为失败。共 12 次请求尝试，已报告 usage 合计 7123 tokens；3 次连接异常没有 usage，不能把 7123 当作完整实际用量。源码前后哈希一致，用例未修改。

该结果触发两项优化：已核验的价格计算直接产出答案，不再调用模型决定 finish；兼容模型的 HTTP 连接由 Harness 实例持有并在关闭时释放，避免 SDK 缓存连接跨测试事件循环复用。已有 `ModelAdapter.close()` 原本为空实现，运行时也未调用它；本地 HTTP 回归验证了修复后两个独立运行实例均一次请求成功且关闭各自连接。该回归没有复现首批连接异常，因此跨事件循环缓存只是异常原因的推测，不能宣称已证明因果。第二批继续使用相同 4 个场景、5 个轮次及请求上限，第一批失败记录保留。

### 真实模型第二批与剩余问题

`eval/live_task_quality_20260908T123245Z_a588f199.json`：仍有 3/4 场景达到预期，构成为正向 2/2、防误判负例 1/2。总计 7 次模型请求、3293 tokens，usage 完整；本批没有连接错误，所有轮次均执行到预期停止点。多轮预算修改正确得到 2 人、总预算 150、两家总价 198/138、差额 60，并推荐满足预算的 138 元选项，未复用旧价格。

剩余失败是未知店价场景中未展示邻店明确的人均 66 元，最终 `places=[]`。页面原文仍被保留，未知目标未被编造价格，也未宣称任务成功；但这些保护不抵消信息漏提取，场景仍记失败。当前脱敏报告没有原始模型回答，无法区分模型漏提取与后处理丢弃。后续应先增加逐阶段的脱敏抽取/过滤原因计数，再针对真实根因修复并扩充未见用例；不应先放宽来源规则或删掉该断言。

两批只有一次运行/版本，同时包含代码变化和模型随机性，不能据此报告总体成功率、稳定性提升幅度或单独归因的性能收益。请求数 12→7 是这两个批次的观测值；首批 usage 不完整，两批 token 数不能当作完整成本对照。

## 验收范围

常规回归、类型检查、构建、迁移与独立启动的复现命令见 README 与 `.github/workflows/checks.yml`。测试计数以命令输出和各报告为准；pytest function 与 subtest 不能相加当作独立业务场景。

最终本地检查记录见 `eval/integration_checks.json`：46 个 Python 测试函数通过（另有 35 subtests）、63 个 Python 文件类型检查通过、39 项真实 Chromium 断言通过；构建、桌面流程、完整后端重启恢复、迁移和独立启动检查均通过。任务质量的 20 个语义场景另按原有五组分母保存在 `eval/task_quality_results.json`。

这批证据不代表生产站点成功率。真实账号、多页面复杂任务、验证码、具体网站预约和下单、支付与外部对账仍需各自验收。当前通用浏览器执行链会明确呈现未完成/待人工核实，不生成模拟订单或排队号补齐结果。Compose 配置和迁移通过，容器构建与服务部署尚未实测。
