# PlanGo — 当前实现设计

本文描述当前仓库的运行路径。安装、部署和验证命令见 [README](../README.md)。，不能代替本轮验收。

PlanGo 是 Electron 本地生活工作台：从用户打开的网页和高德服务取得信息，由项目内 Python Harness 管理规划、浏览器操作、证据、审批与恢复。当前重点是让信息和执行状态可核查。

## 运行结构

| 层 | 职责 | 主要实现 |
|---|---|---|
| 桌面界面 | 聊天、浏览器、行程、地图、来源、确认卡、历史、分享、提醒 | `src/renderer/` |
| Electron 主进程 | 后端启动与认证、可信 IPC、WebContentsView 生命周期、Playwright/CDP 固定操作与回执、局域网分享 | `src/main/harness*.ts`、`browserView.ts`、`browserDriver.ts`、`browser-bridge.ts`、`ipc.ts`、`share/` |
| PlanGo 后端 | 浏览器任务、真实来源读取、价格核验、规划扩展、记忆与提醒 API；缺失实时供给保持未知 | `backend/plango/` |
| 内置 Harness | 任务状态图、模型调用、需求与方案契约、检查点、执行账本 | `vendor/plango_harness/` |

桌面聊天通过统一后端创建和继续任务。界面的步骤流来自任务事件，不据此声称运行了餐饮、玩乐、调研、记忆四个独立子 Agent。Planora 是固定在仓库内的源码来源，运行时无需另一个 Planora 仓库或服务。

实际架构是集中式 Agent Workflow：行程层采用规划、验证、审批与执行准备，浏览器层采用观察和操作交替的 ReAct 循环。确定性协调器管理阶段，Requirement、Planner 等专业节点按需调用模型；`single/multi` 只控制规划视角策略，多人任务可分发 Advocate，不代表自治 Agent Team 或已实现模型并行加速。

默认配置连接 Docker 部署的后端与 PostgreSQL/Redis；可选 `desktop` 模式使用 SQLite 和本地任务消费者。宿主机与容器的 Python 均使用 conda `plango` 环境。浏览器仍由 Electron 提供，单独部署 API 不会在容器内自动生成浏览器会话。

## 规划路径

1. 桌面第一跳是任务负责人；规划节点仅在任务决策为 `plan` 时进入。读取任务、位置上下文、启用的 Skill 和可用记忆，解析需求；缺失或冲突的必要信息通过澄清继续。
2. 普通地理规划优先查询已配置的真实高德服务，不要求预先打开浏览器标签；明确按当前网页规划时读取页面。真实起点、搜索中心和已选门店 ID 分开保存，价格、营业状态、排队等缺失字段保持未知。
3. 将候选编译成行程，结合路线与已有证据核验预算、时间及其他支持的约束。
4. 在工具预算内尝试经济、就近替代，保留锁定站点与时间；替代方案需重新编译和验证。
5. 用户按确切方案 ID 和版本选择或修改；页面展示费用、来源、警告与未核验条件。

需求修改先合并规范再刷新相关事实；预算调整不无条件重搜地点，日期和交通方式变化会重新核验依赖事实。重庆为默认地区，“明天”按已接受用户消息的时区时间锚点解析；未知日期和时分不补成今天或默认到店时间。步行查询不能替换成驾车路线，失败路线的直线下界明确标识为待核验。

候选数量取决于真实供给与验证结果，没有“保证三套”或“绝不返回零方案”的承诺。核验不通过、证据不足和预算耗尽都是需要展示的结果，不能用虚构门店补齐。

## 浏览器与结果证据

工作台内的真实可见浏览器使用 WebContentsView，受管弹窗沿用同一持久会话，主进程通过已适配的 Playwright/CDP 执行操作。renderer 只提交固定用户意图和布局，不持有原始 JS/eval、CDP 或伪造回执权限。浏览器支持导航、观测页面、提取、滚动、点击和输入；观测包含 URL、标签页、快照、页面版本、文本及可交互元素。读取受支持的菜单表格可走确定性解析，复杂抽取与任务决策需要配置模型。

价格比较由代码核算：先确认商家归属与价格口径，再计算人数、总价、预算和差额。套餐总价不能直接当人均，邻店或推荐卡报价不能归给目标店。当前自动完成范围主要是证据充分的人均价格与预算比较；复杂饮食、多目标偏好和未知营业条件仍可能保持部分完成。

截图导入需要支持图像的模型，识别内容标记为用户来源；截图识别本身不能证明网页价格实时有效或比较任务已经完成。

当前网页采用 DOM-first；按需 Vision 使用同一会话的原生截图，每轮有界且仅用于只读理解，无坐标动作。接收迟到的不可变截图回执不代表截图仍可使用：模型读取前仍校验新鲜度、页面与快照绑定。视觉不能绕过登录、验证码、拒绝审批或 UNKNOWN。

## 审批、执行与恢复

输入和点击等写操作先生成审批，审批绑定任务轮次、页面、快照和参数。确认后也会重新检查操作条件；修改需求、页面或表单可能使旧审批失效。登录、验证码或人工接管后需要继续任务并重新观测。

命令状态与回执持久化。恢复时重用已有回执；改变同一命令参数会被拒绝。提交结果不确定时保留 `UNKNOWN`，不能自动重复提交。

澄清、审批和浏览器等待保留剩余执行时间。明确的新用户编辑取得新的有界预算，累计模型和工具用量继续保留；自动恢复、重复命令和单纯批准不补额度。

| 结果 | 能证明什么 |
|---|---|
| 保存草案 `draft_ready` | 保存了指定版本的待核验行程；未知项和已知限制仍保留，不表示可履约 |
| 仅准备 `prepare` / `ready_to_review` | `prepare` 是用户选择的准备范围；只有同一原生表单中的门店/地址、人数、日期、时间及入口核对完成，才返回 `ready_to_review`，仍未提交 |
| 页面交互完成 | 已验证的输入或普通链接导航完成，不证明业务提交 |
| 后续页面观测 | 页面显示了某段确认信息，仍需核对商家、人数、金额等目标 |
| 用户明确核实 | 用户提供核对说明及可选业务编号，结果标记为 `user` 来源 |

通用页面上的“成功”文案不等于预约、取号、支付或外部履约成功。当前没有用模拟订单、模拟排队号补齐正常运行流程的路径。

证据不足可以交付标明限制的草案；进入准备仍需当前可信身份、必要日期/人数及没有已知硬冲突，并保留 `pending_checks`。草案保存和准备确认都不授予提交按钮权限。真实商家准备链仍在同一原运行复验，不能据辅助用例宣布全项目通过。

## 分享、记忆、提醒与 Skill

- 分享前从后端重新核对方案 ID/版本，保存固定快照；局域网链接支持投票和意见，桌面运行且网络可达时可访问。分享内容与反馈在桌面本地持久化，二维码不代表微信渠道已接通。
- 明确偏好、收藏、带来源的任务记忆与用户反馈经后端存储，界面可查看、纠正和删除。支持的只读/准备结果按 run/turn 幂等投影为 episode；不是每段聊天都自动写成长记忆，UNKNOWN 不记成履约成功。Embedding 显式启用，不借用聊天密钥自动发起请求；“越用越准”仍无效果证明。
- 提醒必须由用户显式创建，按时间持久化并支持恢复后补发。提醒文本不自动拥有实时排队、天气或路线证据，也没有微信全天候推送保证。
- 本地 Skill 先展示有限元数据，按需读取启用的正文；文本不能授予额外工具权限，也不能代替具体网站适配。产品运行时尚未实现 MCP client/server，开发工具的 MCP 能力不算产品能力。

## 数据流与隐私

Cookie 保存在 Electron 的持久会话分区，浏览器命令不把 Cookie 直接传给模型或后端。桌面身份、命令回执和分享记录在本机；服务模式的任务、检查点和记忆存于部署后端，`desktop` 模式使用本地 SQLite。

使用远程模型时，对话、相关记忆、网页片段及用户提交的截图可能发送到所配置的模型服务；高德请求也会发送查询与位置信息。分享链接会向持有链接且网络可达的人提供选定方案。因此不能宣称“所有数据绝不出电脑”。

## 验收边界

本地回归包括受控网页、离线模型替身和真实 Electron/Python 组合流程；具体报告注明使用的环境。本轮以真实端到端用户行为验证功能正确性，不开展完整质量指标或角色收益测评。历史离线结果、局部真实试测和真实商家站点验收不能合并成总体成功率。

仍需逐项验收：真实账号与站点差异、多页面复杂任务、登录/验证码恢复、具体商家的预约/取号/下单、支付和外部对账、真实手机局域网体验、长期记忆的推荐效果。微信接入和具体交易适配尚未完成，不能作为当前演示承诺。
